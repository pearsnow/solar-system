# Solar System · three.js WebGPU + TSL

一个把精度拉到素材上限的太阳系，用 three.js r187 的 **WebGPU + TSL** 节点管线实现。

不是某个开源项目的复制，而是针对 8 GB 显存和「视觉优先」重新做的取舍：
真实 J2000 开普勒轨道、拆开的独立贴图、真法线、面向相机的大气辉光。

## 跑起来

```powershell
npm.cmd run dev        # 开发服务器 http://localhost:5173
npm.cmd run build      # 打包到 dist/（29 modules，884 KB / gzip 242 KB）
npm.cmd run preview    # 预览生产版本 http://localhost:4173
```

PowerShell 执行策略禁用了 `npm.ps1`，所以命令要写 `npm.cmd`。

给别人看的时候走 `build` + `preview`：开发模式下 Vite 逐个模块返回，首屏要发几百个
请求（实测约 50 秒）；生产版本只有 19 个请求，HTML 2 秒到位，剩下的是贴图下载与解码。

> `server` 和 `preview` 的 `allowHosts` / `strictPort` 是分开配置的，见 `vite.config.js`。

| URL | 效果 |
|---|---|
| `/` | 太阳系全景（8 行星，真实位置） |
| `/?earth` | 地球特写（8K 材质全套） |
| `/?look=jupiter&dist=6` | 把相机停在某颗天体上（调试入口，Phase 5 会变成真正的聚焦飞行） |
| `/?scale=log` | 对数比例 |
| `/?scale=real` | 真实距离（半径仍放大） |
| `/?q=8k\|4k\|2k` | 强制贴图档位 |
| `/?webgl` | 强制 WebGL2 后端 |

空格键暂停 / 继续时间。

## 轨道精度

不是「看着差不多」。`tools/verify-orbits.mjs` 会把本地解算结果和
[JPL Horizons](https://ssd.jpl.nasa.gov/horizons/) 的官方星历逐点对比。

```powershell
npm.cmd run verify:orbits
```

```
body      date         |Δr| AU      |Δr| km        tol AU      result
mercury   2000-01-01     6.93e-6       1.04e+3      1.0e-4  PASS
venus     1969-07-20     5.26e-5       7.86e+3      1.1e-4  PASS
earth     2026-11-04     4.26e-5       6.37e+3      1.6e-4  PASS
mars      2049-12-31     4.63e-4       6.93e+4      5.3e-4  PASS
jupiter   2000-01-01     7.69e-3       1.15e+6      2.6e-2  PASS
saturn    2000-01-01     2.57e-2       3.85e+6      5.3e-2  PASS
uranus    2000-01-01     7.20e-3       1.08e+6      2.2e-2  PASS
neptune   2000-01-01     7.35e-3       1.10e+6      1.3e-2  PASS
```

**容差不是拍脑袋定的。** 用的是 JPL 官方随表发布的标称误差
（λ 弧秒 / ρ 千公里），换算成距离误差再乘 1.5 的余量。
外行星额外叠加 `1e-2 AU` —— 那是太阳绕太阳系质心的摆动幅度
（木星拉扯，最大约 0.0074 AU），解析表无法描述它，属于物理下限而非实现误差。

内行星误差量级 **1e-5 ~ 5e-4 AU**，这才是这套实现的真实水平。

Horizons 的返回结果会缓存到 `tools/fixtures/horizons.json`，之后离线可复现。
`--refresh` 强制重新拉取。

> 本机 Node 的 `fetch` 连不上 `ssd.jpl.nasa.gov`（undici 连接超时），
> 脚本内置了 PowerShell 回退通道，只在 fetch 失败时启用。

## 贴图管线

```
D:\AgentVenv\Scripts\python.exe tools\build-textures.py
```

下载源图 → 转码 → 按天体各自的上限出档，写进 `public/textures/<level>/<body>/`。
源文件缓存在 `tools/raw/`，重跑不会重复下载（`--force` 强制重新下，`--only sun,mars` 只做指定天体）。

### ⚠️ 源站的 `8k_` 前缀不可信

脚本会打印每张源图的**真实尺寸**，结果和文件名对不上：

| 文件名 | 实际分辨率 |
|---|---|
| `8k_earth_*.jpg` / `8k_mars.jpg` / `8k_mercury.jpg` | 8192×4096 ✅ |
| `8k_sun.jpg` / `8k_jupiter.jpg` / `8k_saturn.jpg` | **4096×2048** ❌ |
| `4k_venus_atmosphere.jpg` | 4096×2048 |
| `2k_uranus.jpg` / `2k_neptune.jpg` | 2048×1024（已是上限） |

所以 `bodies.js` 里的 `textureLevel` 按**实测**填，不是按文件名：
`8k` 只有水星、火星、地球；太阳、金星、木星、土星是 `4k`；天王星、海王星 `2k`。

**天王星和海王星没有更高分辨率可用。** JPL 自己的纹理库里这两颗都标注
`fictional`，天王星的原文是 "Plain solid blue texture. (It's just a solid color,
really!)" —— Voyager 2 只飞掠过一次，而天王星本身几乎没有表面特征。
用 2K 底图 + 极低幅度的程序化条带，比贴一张假的 8K 放大图诚实。

| 输出 | 来源 | 处理 |
|---|---|---|
| `earth/day.jpg` | `8k_earth_daymap.jpg` | sRGB，q92 4:4:4 |
| `earth/night.jpg` | `8k_earth_nightmap.jpg` | sRGB，q92 4:4:4 |
| `earth/normal.jpg` | `8k_earth_normal_map.tif` | 线性，q95 4:4:4 |
| `earth/clouds.jpg` | `8k_earth_clouds.jpg` | 转灰度，q90 |
| `earth/rough.jpg` | `8k_earth_specular_map.tif` | 反相（白=水 → 光滑） |
| `<body>/day.jpg` | `<body>` 源图 | sRGB，q92 4:4:4 |
| `sky/milkyway.jpg` | `8k_stars_milky_way.jpg` | 8192×4096 等距圆柱投影，q90 |

## 按需换档（LOD）

所有天体启动时都是 **2K**，只有相机靠近（< 8 个天体半径）时才升到该天体的原生档位，
离开（> 18 个天体半径）再降回去。两个阈值之间是滞回区，否则停在边界上的物体会每帧重建材质。

**阈值必须按半径算，不能按绝对距离算。** 第一版用了 25 个半径，结果聚焦地球时水星也被
升到了 8K —— 因为内行星彼此只隔几十个显示单位，而水星的半径只有 0.89，25 个半径才 22 个单位。
收紧到 8 之后，只有真正在镜头里的那颗会升档。

换档的实现是**重建实例**而不是替换贴图句柄。TextureNode 的运行时换绑在后端行为上不够确定，
重建虽然要重新编译一次着色器（几十毫秒），但只有一条代码路径，也不会留下着色器状态残留。

实测显存占用（HUD 实时显示）：

| 场景 | 贴图占用 |
|---|---|
| 全部按原生档位加载（不换档） | ≈ 1.27 GB |
| 全景视角（8 天体 2K + 太阳 4K） | **182 MB** |
| 聚焦木星（4K） | 204 MB |
| 聚焦地球（5 张 8K 贴图） | **986 MB** |

全景视角下省掉 86% 的显存，而那时候行星本来就只有几个像素。

## 三个关键实现

**1. 法线用真的，不用亮度假凸起**

官方示例为了省一张图，拿地表亮度当高度做 bump。这里用 r187 的 `normalMap`
节点配 8K 切空间法线，山脉和海岸线是真的。

**2. 大气辉光不能用球壳**

球壳的剪影在数学上必然是硬边圆环：球面在边缘处与视线平行，任何写在该半径上的
衰减都会被挤进不到一个像素。换成面向相机的四边形 + 线性半径，才有真正的柔边。

**3. 轨道压缩是径向的，不是逐轴缩放**

每个位置向量只压缩长度、保留方向。这样行星永远落在它被画出来的轨道线上，
代价是椭圆形状被扭曲。逐轴缩放会让行星偏离自己的轨道。

**4. 土星环的阴影是解析解，不是阴影贴图**

「环上一点朝太阳方向的射线与星球求交」，在着色器里直接解二次方程：

```
disc = (p·L)² − |p|² + 1        // 单位球
t    = −(p·L) − √disc           // 近交点
```

判别式趋零处就是阴影边缘，用 `smoothstep` 得到半影。为一个视觉细节开立方体阴影贴图
（点光源要六个 pass）不值得，而这个解法是精确的、零成本的。

**5. 环的径向坐标在着色器里算，不写进 UV 属性**

第一版把 `u = (r − inner)/span` 写进几何体的 UV 属性，环上出现一层细网格。
排查过程：贴图数据是平滑的、alpha 是平滑的、换成纯色输出网格就消失。
最后定位到顶点属性插值 —— 环的三角形非常细长，属性插值误差在被缩小采样后
变成了可见的栅格。改成每片元从 `positionLocal.xz` 直接算半径，问题消失。

**6. 小行星带要两层，一层不够**

- `InstancedMesh` 岩石：近处有视差和轮廓。尺寸是故意放大的，真实的 100 km 小行星
  在这个尺度下远小于一个像素，看不见的带子不算功能。
- 半透明尘埃环：全景视角下岩石是亚像素的，没有这层带子会直接消失。

带子整体按 4.6 年的平均周期绕太阳转。让 5000 个岩石各自按开普勒速率运动需要每帧
5000 次矩阵更新，而效果在任何实际缩放下都看不出来。

## 已知取舍

| 项目 | 处理 |
|---|---|
| 月球轨道半径 | 真实 0.00257 AU，压缩后不足一像素。改为 5 个地球半径（放大 18 倍），加 5.145° 倾角 |
| 月球大小 | 不走行星的半径压缩曲线，按真实比例跟随地球，否则会被放大到地球的 43% |
| 地月质心 → 地球本体 | 未施加。偏移约 3.1e-5 AU，本尺度下是 0.0015 个显示单位，不可见 |
| 月球轨道 | 只用平均黄经，无摄动项。视觉正确，天文级别不够 |
| 土星环贴图 | 固定 2K。更高分辨率只会和各项异性过滤采样打架，产生拍频 |
